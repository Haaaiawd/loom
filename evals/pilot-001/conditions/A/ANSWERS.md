# User answers to Condition A

1. 团队是 3 人远程独立游戏团队：制作/设计、程序、美术。每个人在自己的 Windows 电脑上使用；首版不做多人共享。不同角色可以看到不同候选，但不能把人锁死在角色里。
2. 最大痛点是隔天忘记项目最近发生了什么，以及 backlog 混在一起后不知道今天从哪里切入。目标是打开后 2 分钟内选定一个可开始的动作；不是让工具替人制定完整日程。
3. 工具给出 3 个带证据和理由的候选，并指出风险或阻塞；最终由人选择、跳过或说明今天的目标。不要把算法排序包装成唯一正确答案。
4. 原型只读取本地 Markdown backlog 与 Git 历史，保持引擎无关。暂不读取外部 issue、构建服务或引擎专属文件。
5. 对游戏项目严格只读，不改 backlog、不提交 Git、不执行项目命令。工具可以在自己的本地数据目录记住用户上次选择，但写入前要清楚说明。
6. 全程本地、离线、无账号、无遥测，不上传源码或元数据；首版不调用联网模型。
7. 使用提供的 sample-project 验收。核心路径是：选择文件夹 → 看最近变化与未决事项 → 看 3 个带理由候选 → 选择或跳过一个 → 下次打开看到上次选择。Windows 11；原型可用本地 Node 服务加浏览器界面和双击启动脚本，不要求安装包。
8. 明确不做聊天、云同步、工时追踪、完整项目管理、自动拆任务、自动写回项目。视觉上希望像安静的工作台，不要 Kanban 仪表盘，也不要积分、连续签到等游戏化装饰。

样例中程序成员当前应首先看到“调查强退期间的存档损坏”，因为它可能造成玩家数据丢失；但界面必须说明这是基于风险的候选，而不是替团队拍板。若用户今天是美术，则候选应随角色与今日目标改变。

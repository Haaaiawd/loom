# 初步工作计划

## 施工原则

- 只维护一个纵向切片，优先打通真实用户路径；
- 每一阶段都以可观察证据结束，不以“文件已创建”作为完成；
- 先固定契约和黄金结果，再写界面，避免漂亮页面掩盖读取或解释错误；
- 对 sample fixture 与真实 Git 仓库分别验证，不能用 `GIT_LOG.txt` 冒充真实 Git 能力；
- 任何测试不得修改 `sample-project`。

## Work Map

### W1：工程骨架与契约

目标：得到可启动的 loopback Node 服务、静态页面和稳定领域类型。

工作：

- 选择最小 Node 工程结构与依赖；
- 固化 `ProjectSnapshot`、`Candidate`、`LocalState` schema；
- 建立 `start.cmd` 的服务启动、健康检查和打开浏览器流程；
- 添加会话 token、Host/Origin 保护的最小骨架。

验收：双击可打开本地空壳页面；仅监听 `127.0.0.1`；外部 Host 请求被拒绝；端口冲突不杀未知进程。

### W2：只读项目扫描

目标：从真实目录生成可追溯 snapshot。

工作：

- 实现目录规范化和读取白名单；
- 解析普通 Markdown 无序列表并保留行号；
- 实现 `GIT_LOG.txt` fixture adapter；
- 实现真实 `.git` 只读 adapter；
- 建立文件缺失、格式错误、超限、超时的错误模型。

验收：

- `sample-project` 得到 5 个 backlog 项和 4 条 fixture commit；
- 另建测试仓库验证真实 Git adapter 得到正确短哈希和 subject；
- 扫描前后对 sample-project 做内容摘要比较，确认零变化；
- 无 `.git`/log、空 backlog、恶意路径和超大文件均有明确结果。

### W3：候选与解释引擎

目标：对同一输入稳定地产生可追溯、互有差异的候选。

工作：

- 实现 tokenizer、受控词表和 backlog 类型标注；
- 实现风险/阻塞、近期连续性、角色/目标相关性规则；
- 实现三个理由槽位、去重、稳定 tie-break 和跳过补位；
- 实现理由模板与证据完整性检查；
- 将规则版本写入 snapshot/响应，便于后续回归。

黄金验收：

- 程序角色、空目标：存档损坏调查是风险导向首要候选，理由引用 backlog 与存档相关 commit，并使用“可能相关”；
- 美术角色：flooded archive ambience 与 capsule images 的相关性上升，但高风险项不会因角色消失；
- 输入“playtest”：capsule images 的目标相关性上升；
- 相同输入重复运行结果一致；
- 少于 3 个 backlog 项时不伪造；每个事实性理由都有 evidence ref。

### W4：本地状态与同意

目标：选择可以跨重启恢复，项目仍保持只读。

工作：

- 实现首次保存说明与同意状态；
- 实现原子写入、schema version 和损坏状态恢复；
- 保存 lastDecision 候选快照；
- 实现清除选择与清除全部本地记录。

验收：选择后重启仍显示原决定；源 backlog 删除该事项后只提示“未找到”，不判定完成；拒绝保存时主路径仍可用；写入失败有可见提示。

### W5：单页工作台

目标：完整实现两分钟内选择切入口的 UI 路径。

工作：

- 实现首次打开、文件夹选择/路径降级；
- 实现来源摘要、最近变化、未决事项；
- 实现角色、今日目标和显式更新候选；
- 实现候选证据展开、选择、跳过、换一个；
- 实现上次选择、错误态、窄窗口和键盘流程；
- 按 `EXPERIENCE.md` 完成视觉与文案。

验收：新用户无需说明可从 sample-project 走通核心路径；正常宽屏和窄窗口无横向溢出；键盘可完成选择；界面无伪分数、Kanban 和游戏化元素。

### W6：端到端验证与交付

目标：证明原型的运行、安全、隐私和产品契约。

工作：

- 自动化端到端核心路径；
- 双击启动冷启动验证；
- 断网环境运行；
- 监听地址、网络请求和项目目录写入审计；
- 手工计时可用性走查；
- 写明安装前提、启动、停止、清除状态和已知限制。

完成标准：

- Windows 11 上双击启动成功；
- sample-project 完整路径可运行，关闭重启后恢复选择；
- 典型首次使用能在 2 分钟内做出选择；
- 项目目录哈希/文件清单前后一致；
- 只有 loopback 网络活动，无遥测与外连；
- 真实 Git adapter 有独立测试证据；
- 所有失败边界不把“未知”伪装成空结果或成功。

## 建议的第一项当前 Task

开始施工时，只详细展开 **W1 + W2 的最薄纵向部分**：

> 建立可启动的 loopback 服务，并让 `/api/projects/scan` 对 `sample-project` 返回 5 个带行号的 backlog 项、4 条明确标注为 fixture 的 commit，且扫描前后项目目录完全不变。

暂时不要先做候选卡视觉，也不要创建完整规则词表。这个 Task 能最早验证系统边界和输入真实性，是后续全部体验的地基。

## 回归清单

- [ ] 服务仅绑定 loopback
- [ ] UI 无外部资源请求
- [ ] 项目读取白名单生效
- [ ] 不调用 Git CLI 或项目命令
- [ ] sample fixture 与真实 Git 两条路径没有混淆
- [ ] backlog 文本、行号、commit hash/subject 可追溯
- [ ] 三个候选不重复且理由有差异
- [ ] 角色只加权，不过滤
- [ ] 今日目标改变候选有可见理由
- [ ] 选择、跳过、重选均可逆
- [ ] 首次写入前有说明/同意
- [ ] 重启后恢复上次选择但不声称完成
- [ ] 清除本地记录有效
- [ ] 项目目录零写入
- [ ] 无账号、遥测、联网模型或外连
- [ ] 错误态不把未知说成成功

## 暂缓项

以下事项只有在纵向原型证明核心价值后再评估：复杂 Markdown、多个 backlog 文件、diff 分析、多语言语义、本地小模型、多项目、团队同步、引擎适配、安装包。它们都不应提前进入首个实现 Task。

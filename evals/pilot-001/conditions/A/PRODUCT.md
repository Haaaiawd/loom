# 开工台：产品全貌

> “开工台”是工作名，不是已经确认的品牌名。

## 一句话定义

一款完全本地、项目只读的 Windows 晨间工作台：它把最近 Git 变化与 Markdown backlog 联系起来，给出三个有证据、可反驳的开工候选，最终选择权始终属于用户。

## 用户与问题

目标团队是 3 人远程独立游戏团队：制作/设计、程序、美术。每个人在自己的 Windows 11 电脑上独立使用，不共享工具状态。

核心问题不是团队缺少完整的项目管理器，而是：

- 隔天后很难快速恢复“最近发生了什么”；
- 混合型 backlog 把缺陷、决策、内容、调查和发布事项放在一起，缺少当天切入口；
- 不同角色需要不同相关性，但独立团队成员经常跨职能，不能被角色过滤器锁死。

## 成功定义

用户从打开工具起，在 2 分钟内完成一次有依据的决定：选择一个可以开始的动作，或者明确跳过候选并补充今天的目标。

首个纵向原型的成功路径：

1. 选择 `sample-project` 文件夹；
2. 看见最近 Git 变化与全部未决事项；
3. 选择或调整角色，可选填今天目标；
4. 看见 3 个各有理由、证据和风险/阻塞说明的候选；
5. 选择一个候选，或跳过并重新表达目标；
6. 关闭并重新启动后，看见上次选择及时间，但工具不把它误报为“已完成”。

## 核心产品原则

1. **事实和推断分开。** backlog 原文、commit 摘要属于事实；“高风险”“与近期改动相关”属于工具推断，必须标明依据。
2. **建议不是裁决。** 只提供三个候选，不出现“唯一正确”“AI 已决定”或伪精确的排名分数。
3. **角色只加权，不设墙。** 程序成员仍可看到重要的设计或美术事项；跨角色的高风险事项不能被隐藏。
4. **少而完整。** 产品只解决恢复上下文与选择开工动作，不扩张成完整日程或项目管理系统。
5. **隐私边界可见。** 扫描前说明读取范围，候选上能查看出处，首次保存工具状态前说明保存内容与位置。
6. **选择可逆。** 用户能换角色、修改目标、跳过候选或重新选择，不需要维护复杂状态。

## 首版范围

### 输入

- 用户明确选择的单个本地文件夹；
- 根目录中的 Markdown backlog（原型约定文件名 `BACKLOG.md`）；
- 本地 Git 仓库的近期提交历史；
- 验收夹具中的 `GIT_LOG.txt`，作为明确标注的模拟 Git 历史来源；
- 用户选择的当前角色：制作/设计、程序、美术、不限定；
- 可选的“今天想推进什么”自由文本；
- 工具自己保存的上次选择。

### 输出

- 最近变化摘要，保留 commit 短哈希和原始 subject；
- 未决事项列表，保留源文件和行号；
- 恰好 3 个互不重复的开工候选；
- 每个候选的动作、推荐理由、原始证据、风险或阻塞提示、角色/目标相关性；
- 上次选择的只读回顾。

### 工具允许写入的内容

仅写自己的 `%LOCALAPPDATA%` 数据目录，包括项目路径、角色、今日目标、跳过记录、候选快照和上次选择。首次写入前必须告知用户；提供“清除本地记录”。

### 明确不做

- 修改 backlog、Git 或任何游戏项目文件；
- 执行游戏项目命令、构建、提交或脚本；
- 聊天、云同步、账号、遥测、联网模型；
- 工时追踪、完整项目管理、自动拆任务、自动写回；
- 多人共享、多项目总览；
- Kanban、积分、连续签到或其他游戏化装饰；
- Unity、Unreal、Godot 等引擎专属读取。

## 候选判断模型

首版使用可解释的确定性规则，不使用模型。内部可以计算离散权重，但界面不展示总分或置信度百分比。

每个 backlog 项只从以下角度形成推断：

- **损失风险：** 数据损坏、崩溃、阻断测试等潜在后果；
- **阻塞/不确定性：** `investigate`、`decide` 等事项是否能解锁后续工作；
- **近期连续性：** backlog 词语、对象或场景是否与近期 commit 有可解释关联；
- **角色相关性：** 当前角色是否更容易直接开始，但只作为加权；
- **今日目标：** 与用户输入是否有明确词语或受控同义词匹配。

三个槽位优先覆盖不同理由：

1. 风险或阻塞候选；
2. 与近期改动有连续性的候选；
3. 与角色或今日目标最相关的候选。

若同一事项命中多个槽位，只出现一次；空缺槽位从剩余事项中补齐，并诚实显示较弱的理由。若 backlog 少于 3 项，不伪造候选，界面显示实际数量并说明原因。

## 样例的预期判断

程序角色且没有填写今日目标时：

- “Investigate save corruption reported after force-closing during scene transition.” 应是首要候选，因为玩家数据丢失属于高损失风险，并且它与近期 `preserve inventory after checkpoint reload` 存在可调查而非已确认的关联；
- 另外两个候选应优先从 camera jitter、tutorial/ranged enemy 等程序或近期连续性较强的事项中产生；
- 界面必须说明“风险导向候选，不代表团队优先级已经确定”。

美术角色时：

- flooded archive ambience 可关联最近的 flooded archive lighting commit；
- capsule images 与美术/内部 playtest 相关；
- 高风险存档调查仍可作为跨角色提醒出现，而不是被角色过滤掉。

以上是验收用的方向性黄金结果，不要求候选理由逐字相同。

## 产品专业判断

### 为什么不直接生成“今日计划”

本地可见信息只有 backlog 与 Git 历史，不包含团队承诺、截止日期、真实依赖和个人精力。生成完整日程会把信息缺失伪装成智能；三个候选更符合证据能力，也保留用户能动性。

### 为什么不做纯排序列表

排序会把混杂事项压成一个不可解释的数字。三种理由槽位能维持候选差异，让风险、连续性和个人目标同时进入视野。

### 为什么保留上次选择而不追踪完成状态

“上次选择”能恢复个人上下文；“完成状态”则开始复制项目管理器，并可能与真实 backlog 冲突。首版只记决定，不声称工作状态。

## 已知限制与开放项

- 关键词和浅层文本关联会漏掉隐含语义，也可能产生误关联；证据展示和用户否决是必要保护，不是装饰。
- 中文今日目标与英文 backlog 的跨语言匹配在无模型条件下能力有限；原型只承诺关键词及小型受控词表。
- 样例目录不是完整 Git 仓库，因此 `GIT_LOG.txt` 只能验证界面与候选闭环；真实 `.git` 读取必须另有测试夹具验证。
- `BACKLOG.md` 的复杂格式尚未定义。原型只承诺普通无序列表；复选框、分组、优先级字段属于后续兼容项。
- 产品正式名称和视觉品牌尚未决定，不阻塞纵向原型。

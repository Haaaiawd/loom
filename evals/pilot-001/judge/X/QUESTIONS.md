# 当前理解

我们要做的不是另一个通用待办清单，而是一个 Windows 本地桌面“开工入口”：它读取现有独立游戏项目留下的真实痕迹，帮助小团队迅速恢复上下文，并得到可信、可解释的下一步。第一个成果还不是完整产品，而是一个能跑通这段核心体验的纵向原型。

样例项目目前只提供了 Git 历史与 backlog，但已经包含程序、设计、美术、发布准备和高风险故障等不同类型的工作。因此，真正会改变产品形态的地方是：为谁做决定、读什么证据、如何判断优先级，以及工具可以替团队走到哪一步。

# 需要你一次确认的问题

1. 第一个版本首先服务谁：亲自写代码或做内容的成员、制作人/主策，还是整个团队？打开工具两分钟后，最重要的结果是一条明确的下一步、带理由的短清单，还是一份可共同确认的今日计划？原型是否必须让多人共享状态？

2. 除了本地 Git 历史和 Markdown backlog，原型还应读取哪些信息（例如未提交改动、项目文档、构建/测试结果、引擎文件或外部任务系统）？不同来源冲突时以什么为准？首版是否应限定为全程本地、离线、只读——不修改项目文件，也不执行项目命令？

3. 首个纵向原型应做成与引擎无关的“项目文件夹读取器”，还是应优先针对 Unity、Godot、Unreal 或你们正在使用的某一种项目？如果针对具体引擎，请告诉我引擎、版本，以及真实项目中稳定可读的关键文件。

4. 判断“下一步”时，哪些因素必须压过其他因素：已分配负责人、里程碑或截止时间、故障严重性、阻塞关系、最近修改、成员角色，还是当天可用时间？工具可以主动推断并给出首选项，还是只能陈列证据、由人最终挑选？

5. 用样例校准一下：在“强退后可能存档损坏”“Boss 场景相机抖动”“教程顺序待决”“替换环境音”“准备试玩胶囊图”之间，你希望工具此刻优先推荐哪一项，为什么？如果单凭现有信息本就不该下结论，也请说明它还必须向用户取得什么信息。

6. 你认定的最小可运行闭环是否是：选择项目目录 → 读取 Git 与 backlog → 呈现证据摘要 → 推荐下一步并解释理由 → 用户接受或跳过 → 下次打开仍记得这次选择？其中哪些环节不可缺少；原型只需在提供的 `sample-project` 上演示，还是必须能读取一个真实游戏仓库？

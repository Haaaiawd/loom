# LOOM 使用路径审查

审查日期：2026-10-18。对象：当前工作区 LOOM 2.1.3 源码。负责人意图：从使用者角度看清完整旅程及副分支，尤其是存量仓库接入、途中改变项目、途中改变 LOOM。此次只审查和制作视图，不修改运行时，不发布包。

## 当前判断

主交付循环已具备实用的结构保障：初始化、理解记录、设计与能力卷宗、任务依赖、首次 Keeper、执行、逐项证据、阻塞与重开、上下文恢复。现有 28 项端到端测试全部通过。

分支的成熟程度并不一致。接入既有仓库后的事实重建、需求变更的影响识别、LOOM 升级后的协议同步、已完成下游任务的失效判断、损坏状态恢复，仍依赖宿主 Agent。CLI 检查的是可检查的结构，不是结果真实成立，也不是业务完成证明。

最决定后续优先级的两个问题：①外部变化后，哪些旧理解、审查和完成证据还有效？②下一位 Agent 能否知道自己处在哪条恢复路径，而不是只看到合法文件？主流程继续增加字段，不一定能解决这两点。

## 路径全景

主干：入口与识别 → 理解与澄清 → 设计/能力/交付面 → 首次独立交接 → 选择与执行任务 → 证据与覆盖 → 完成或继续。恢复、变更和升级可以在任何阶段横切主干。

| 分支 | 用户实际遇到的情况 | 现有行为与责任 | 回到哪里 |
| --- | --- | --- | --- |
| 新建 | 空仓库开始 | init 生成骨架；Agent 写当前理解，不能把模板当已理解 | 塑形 |
| 接入 | 已有代码但没有 LOOM | 保留源码与原规则，追加锚点；不自动识别架构、风险或历史决定 | 事实重建后塑形 |
| 接入 | 仓库已有多套规则/文档 | Agent 识别冲突及权威，不机械覆盖 | 对准真实目标 |
| 接入 | 子目录/monorepo | context 向上寻找最近 state.json；init 使用当前目录，可能建立另一边界 | 先明确工作区根 |
| 接入 | 已有 LOOM v2 | init 直接返回 already_initialized；context 恢复 | 当前任务 |
| 接入 | LOOM v1 或未知 schema | 已知 legacy 目录拒绝覆盖；未知 schema 加载失败；无自动语义迁移 | 备份、显式迁移 |
| 塑形 | 目标不清/答案改变理解 | Agent 自适应提问，record/decision 更新事实与设计 | 继续澄清 |
| 塑形 | 用户不可用或要求先做 | 人类通道不可用时记录可逆假设，权威不足则阻塞；不虚构用户确认 | 有界执行或等待 |
| 能力 | 需要专业判断 | add/research/synthesize/confirm；领域树由 Agent 编写，不是 CLI 自动研究 | 设计与任务 |
| 能力 | Agent 暂选/研究结论变化 | 暂选有 provisional 状态；重新研究后重建决策树；受影响任务由 Agent 查明 | 更新设计和任务 |
| 计划 | 大项目/依赖未满足 | Work Map 留盘；上下文聚焦当前任务；依赖完成后才能 start | 可执行任务 |
| 计划 | 很小的修复 | 初次 ready 仍需真实 PROJECT、设计与非空任务图；任务可有设计/能力豁免，项目级 ready 没有等价轻量入口 | 明确流程代价 |
| Keeper | 首次通过 | 宿主新开无继承 Agent；摘要、唯一 run_id 和独立声明留痕 | build_ready |
| Keeper | 需修订/阻塞 | 原文具体 gap 进入下一轮；变更摘要后独立复查，历史未闭合 gap 不能丢 | 塑形与重新交接 |
| Keeper | 无独立环境 | 显式 skip 留原因；降低证据强度，不称独立通过 | build_ready |
| Keeper | 审查途中改输入 | 已纳入摘要的文本改变后拒绝旧摘要；STRUCTURE、源码、研究文件等不在摘要内 | 重新准备受影响审查 |
| 执行 | 正常单任务 | 精确 reads、实现/能力归属、依赖和单 active 检查 | 验证与 done |
| 执行 | 同一任务中断/换 Agent | context 恢复任务、reads、hooks；Agent 对照 Git、实际文件和 progress | 继续当前任务 |
| 执行 | API/登录/外部权限缺失 | block 写原因和恢复条件，之后有理由 reopen | 任务选择 |
| 执行 | 新急事打断当前任务 | 无 pause/suspend/cancel；单 active 限制意味着只能 block 当前任务或改写其范围 | 人工维护任务边界 |
| 执行 | 多 Agent/多终端 | 一个 active 约束不等于写入锁；无跨命令事务与并发冲突保护 | 单写者或隔离工作区 |
| 变更 | 颜色/文案/局部 bug | 不改变设计/验收时直接修并验证 | 当前任务 |
| 变更 | 改目标/验收/边界 | decision → 当前设计 → task update/reopen；CLI 不推断所有影响 | 新任务图 |
| 变更 | 推翻已完成上游 | 可重开，但已完成下游不自动失效；Agent 需检查依赖闭包 | 重验受影响下游 |
| 变更 | 人直接编辑文件 | Markdown 当前真相可编辑；无语义差异识别，未写 affected_tasks 不会自动找到旧完成声明 | 对齐后继续 |
| 变更 | 取消功能/缩小范围 | 没有取消/废弃任务和删除交付单元的正式命令；不应靠假 done 清图 | 显式决定并整理计划 |
| LOOM 变化 | 工作中升级 CLI 包 | 当前仅校验 schema_version=2，不记录生成协议的包版本；兼容 schema 不保证协议同步 | 备份、版本核对、回归 |
| LOOM 变化 | 修改本仓库 LOOM 源码 | 已落盘 AGENTS 是旧快照，context 协议取自新代码；全局安装也可能仍旧 | 测源码/安装副本，核对锚点 |
| LOOM 变化 | 仅修改项目 .loom 文档 | 属于项目决策演化；不要混同 CLI 升级 | 变更流程 |
| LOOM 变化 | 降级/跨 schema | 不兼容 schema 拒绝；无自动回滚/迁移事务 | 恢复成套代码与状态 |
| 恢复 | JSON 损坏/初始化半途失败 | 加载报错；只要 state.json 存在，init 不补齐；无 repair/doctor | 备份比对与定点修复 |
| 恢复 | 丢失 AGENTS 锚点/忘传 sidecar | check 不检查普通锚点；sidecar 每次都需相同参数 | 找回入口与状态位置 |
| 恢复 | Git 分支/合并/回滚 | 无分支身份或合并语义；依赖 Git 与 Agent 协调代码、文档、状态和证据 | 一致快照后 context |
| 完成 | 输出缺失 | 新任务 done 检查本地 touches 存在，check 可发现之后删除 | 修复与重新验证 |
| 完成 | 输出还在但内容错 | 存在检查不是正确性证明；证据文本不由 CLI 实际执行 | 真实验证任务 |
| 完成 | 所有任务 done 但交付缺项 | complete 由任务状态触发；未覆盖交付只 warning，healthy 仍可 true | 验证交付面 |
| 完成 | 已 complete 又新增工作 | plan/reopen 将项目恢复为 building；不用每任务重跑 Keeper | 新任务循环 |
| 完成 | 交付上线/发布受阻 | 文件验收、外部发布、真实使用是不同证据；本仓库发布任务受凭据阻塞 | 外部条件满足后复核 |

## 最需要补强的断点

### 1. 变化发生后的有效性维护（优先）

事实：P06 重开上游，依赖它的已完成下游仍 done，check 无相关提示。`store.js:690` 只改目标任务；`checkProject:1016` 未验证 done 任务的依赖仍 done。`recordDecision:916` 只记录 Agent 给出的 affected_tasks；漏列就没有影响警告。

影响：用户一句“我们改成另一种方案”，主链可能更新而旧证明继续看似成立。最小方向：计算依赖影响范围，区分“待复核”与“已失效”，让 Agent 明确处置，不机械把所有下游重做。

Keeper 通过后并非永久语义保证。`startTask:718` 不复核摘要；这是“一次交接”的设计边界。需要补的是实质变更后的阶段复核，而不是每任务重跑首次 Keeper。P12 进一步表明 STRUCTURE 的变化不会改变摘要，当前冻结范围应明确展示。

### 2. CLI、协议锚点、项目状态的版本关系（优先）

事实：P02 重跑 init 保留旧锚点。`initProject:99` 在 state 存在时提前返回；`installAgentAnchor:146` 以 marker 决定是否追加；state 仅有 schema 版本，未绑定 CLI/protocol 版本。`projectDigest:834` 未覆盖 CLI、STRUCTURE、deliverables、源文件或研究文件。

影响：升级 LOOM 不等于更新现有项目里的协议；修改源码不等于修改全局安装。最小方向：记录 CLI/schema/protocol 来源；提供可审阅的协议同步与迁移预检，保留原 AGENTS 规则；升级前后在隔离副本跑 context/check 和代表任务。没有执行实际 npm 升级，后果为源码推断。

### 3. 恢复建议需要反映可执行现实（其次）

事实：P08 活跃任务中调用 ready，project=ready_for_keeper、task=active、keeper 仍 skipped；context 优先建议交接。审查前本仓库也存在 ready_for_keeper + skipped + 无 active + 三 blocked 的组合。`markReady:798` 不限制 active；`compileContext:939` 优先项目状态。

最小方向：验证跨状态不变量，按活跃工作、待审查输入、阻塞条件给出一致的下一步；ready 不应无提示遮住执行恢复。

### 4. 接入、暂停、取消、损坏恢复（其次）

接入是安全脚手架，不是棕地理解器（P01）。有用的接入流程应采样现有架构、测试、未提交修改、既有约束与生产现实，再按本次需求建立最小可信基线。

没有 pause/cancel/migrate/repair/upgrade 命令；这是当前能力边界，不是每个项目一定发生的 bug。P03 证实损坏 JSON 时 init 不修复；P09 证实锚点丢失未被 check 识别。`atomicJson:46` 保护单文件替换，不提供多个 JSON 和 Markdown 的事务，也没有并发锁。并发和断电风险尚未注入测试。

### 5. 健康、完成、交付要分别呈现（其次）

P07 未覆盖交付存在时 project=complete、healthy=true。`completeTask:790` 依据所有任务 done；`checkProject:1080` 对未覆盖只 warning。这可以是合法的结构语义，但用户容易把它听成项目已交付。建议视图和输出分别说明：结构完整性、任务完成度、交付覆盖、真实结果验证。

## 建议的后续顺序

先处理变更影响与状态建议一致性，再补 CLI/协议升级与既有仓库接入，最后完善暂停取消和故障恢复。每项都应从具体分支探针倒推验收，不把此次审查直接扩成一轮无边界重写。本轮交付审查结果和路径视图，运行时代码未改。

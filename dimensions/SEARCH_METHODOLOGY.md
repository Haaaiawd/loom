# Decision-Driven Research

研究是减少北极星、能力边界和关键取舍判断错误的第一道门。在落笔任何
长期 Doctrine、愿景 narrative、架构契约或实现方案前，默认先问：
**如果没有外部证据，我会不会只是在臆断？**

研究不是“显得充分”的仪式，而是把主观判断转成可追溯证据的核心步骤。

## Research Gate

产出以下任何产物前，先完成这个检查：

1. 写出当前决策问题（它会改变什么选择、范围或验收）。
2. 列出已经掌握的项目事实和外部事实。
3. 识别仅凭项目事实无法回答、且会影响结果的问题。
4. 对这些问题进行 Targeted Search，提取机制与边界。
5. 把证据翻译成项目后果，写入 Evidence Map 或 Expertise Pack。
6. 当仍有不可消除的不确定性时，先询问用户，而不是默认假设。

## 触发条件

满足任一条件即必须启动外部研究：

- 北极星、目标用户、关键场景或能力边界尚未由项目事实充分定义。
- 决策具有高影响、不可逆或跨 Intent 影响。
- 任务需要专门领域知识、质量判断或安全边界。
- 已有方案“合格但普通”，需要寻找不同机制。
- 证据互相冲突，需要确定适用条件。
- 声称“更好、出众或胜过原版”时，需要基线相对的测量或案例。

只有在**项目内事实充分、低风险且可逆**时，才可以直接实验而不先做外部搜索。

## 搜索回路

```text
Decision Question
→ Project Grounding
→ Targeted Search
→ Extract Mechanism
→ Translate to Project Consequence
→ Test or Record
```

### 1. Decision Question

把未知写成会改变行动的问题，例如：

- 哪一种交互机制能让首次使用者更快建立正确心智模型？
- 该库在当前数据规模下的失败边界是什么？
- 什么信号能区分视觉新鲜感与长期可用性？
- 目标用户真实使用的替代方案及其不满意点是什么？
- 宣称“更快/更安全/更易用”的基线是什么，如何测量？

“了解行业最佳实践”不是问题。

### 2. Project Grounding

先读真实仓库、用户反馈、现有产物、约束和历史决策。外部资料不能替代项目事实，
但可以补充项目事实触及不到的边界、机制和市场证据。

### 3. Targeted Search

选择与主张匹配的来源：

- 协议、行为、接口 → 官方规范与实现文档。
- 风险、效果、因果 → 原始研究、测量或真实案例。
- 品味与作品质量 → 代表作品、设计批评、成熟实践者的可验证方法。
- 当前工具能力 → 当前官方文档和真实运行结果。
- 市场/用户/竞品 → 可验证的使用场景、真实反馈和失败案例。

来源数量不设下限或配额。一个直接原始证据可以足够；多个间接来源也可能仍不够。
宁可只有一个能改变决定的强证据，也不要一堆只能“看起来充实”的弱来源。

### 4. Extract Mechanism

不要只抄结论或名字，提取：

- 在什么条件下成立。
- 通过什么机制产生结果。
- 可能在哪些条件下失败。
- 它能否迁移到当前项目。

### 5. Translate

每条保留证据都要落成项目后果：

```text
Evidence → Mechanism → Project Decision → Verification Signal
```

无法改变决定、候选或验证方式的资料不进入正式上下文。

### 6. Stop

满足以下任一条件停止：

- 新证据不再改变候选排序或边界。
- 一个低成本实验比继续阅读更有信息量。
- 已有证据足够支持可逆决定。
- 不确定性只能由用户授权或真实反馈消除。

**未满足以上条件前，不得为了“赶快落笔”而停止搜索。**

## Evidence Map

长期判断写入 Doctrine 的 Evidence Map；任务级专业资料进入临时 Expertise Pack；实现后的比较结果进入
Quality Proof。三者不要互相复制成第二真相源。

最低记录：

- 来源或项目事实。
- 为什么与当前问题相关。
- 提取的机制或边界。
- 它改变了什么决定。
- 可追溯位置。

## 失败模式

- 固定凑来源数量。
- 用权威名字代替适用性。
- 先搜索后定义问题。
- 把“大家都这样做”当证据。
- 搜到熟悉答案就停止。
- 把任务级技巧永久写入 Doctrine。
- 只有结论，没有基线、反例或验证信号。
- 以“项目里没人要求”为由跳过研究。
